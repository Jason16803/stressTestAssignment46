# Assignment 4.6 — JMeter Stress Test

Cloud-only workflow in GitHub Codespaces. The application is copied from [the instructor repository](https://github.com/brandonbrown/wdv4416-4-6-stressTest), revision d31bd1cc707c08e4a5533ccb9aa7a2787e2f75d0. Its server, routes, schema, and dependency lockfile are preserved under app/ with whitespace normalized.

## Start the environment

```bash
bash scripts/setup-jmeter.sh
(cd app && npm ci)
bash scripts/start-app.sh
```

MongoDB 7 runs in the assignment46-mongo Docker container, bound to 127.0.0.1:27017. The application runs on port 3000. Its output is in .runtime/app.log. The launcher selects IPv4 first so the instructor's localhost database URL works with the Docker binding. The default Java installation is unchanged; scripts/jmeter.sh selects OpenJDK 17.

## Run and generate both reports

```bash
bash scripts/run-test.sh smoke
bash scripts/run-test.sh stress
```

The smoke test uses a separate copy of the plan with 5 users and 2 loops. The submitted plan in tests/stress-test.jmx retains:
- HTTP Header Manager: Content-Type = application/json
- 10,000 users, 1-second ramp-up, 2 loops, continue after sampler errors
- POST http://localhost:3000/
- View Results Tree -> results.csv
- Summary Report -> summary.csv

The body uses synthetic strings only: ccNumber TEST-ONLY-0000, expiration 12/2030, ccv 000. An assertion checks HTTP 201. Connection and response timeouts are 10 and 120 seconds.

Each run gets a fresh UTC-stamped directory under runs/. JMeter executes in non-GUI mode, writes results.jtl and jmeter.log, then generates reports/results/ and reports/summary/ from the two listener CSV files. No old run is overwritten. The two reports describe the same run and should contain the same samples.

scripts/check-results.py checks the expected sample count, matches the core sample fields across all three data files without relying on concurrent write order, verifies both report entrypoints, and writes metrics.json. Application errors are reported, not hidden.

## Cloud measurement limits

The load generator, API, and database share this 2-core, 8-GB Codespace. Its cgroup process/thread limit was 9,502 at setup. Configuring a 1-second ramp-up does not guarantee the machine actually starts 10,000 threads within that time. Use console.log, jmeter.log, and metrics.json to distinguish configured users from achieved concurrent users. These are measurements of this shared development environment, not production capacity. JMeter uses a 2-GB maximum heap and 256-KB thread stacks for this run.

This packages the latest completed stress run, both HTML report folders, shell scripts, JMX, JTL, CSV files, jmeter.log, source, and instructions. The output is under submission/. It excludes downloaded tools, node_modules, and MongoDB storage.

## Files and persistence

Setup and source are tracked in Git. Runs, tools, temporary application logs, dependencies, and new ZIPs are ignored. The verified submission ZIP from this run is explicitly tracked under submission/. A result summary is tracked in RESULTS.md after verification. Download the ZIP before deleting the Codespace.
